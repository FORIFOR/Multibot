How it works

The Master plans. Bots do the work. The runtime checks.

1. The plan is structured output

The Master emits deliverables, acceptance criteria and a task DAG. The runtime validates schema, cycles, owners, tool scope and write scope, and sends an invalid plan back once.

2. Work is real messages and real files

A bot-to-bot message is a recorded delivery into the other bot's mailbox, not a script. Deliverables are immutable revisions with a SHA-256 hash.

3. Verification binds to a revision

Checks and review verdicts attach to a revision hash. The final report is compiled from the event log, so a model summary cannot upgrade “started” to “done”.

Budgets, call limits, permissions, approvals and cancellation are enforced by the runtime, not by prompt wording. Builder and Reviewer commands run in Docker (no network, read-only root) or the macOS seatbelt; with neither, they are refused.

Why one failed and one is partial

The first attempt exposed a scheduler deadlock: a task depending on a task that itself awaited review waited forever. Fixed, with a test. The re-run got through the fixes and re-verification, but the review session hit its $1.5 budget cap twice, leaving the line-by-line source check undone. Research-heavy requests are the most expensive and the least stable.
