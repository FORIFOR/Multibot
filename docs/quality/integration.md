# Integration contract (0.2.1 working-tree extension)

This document describes the local patch based on `9afbfe4`; it is not a released version announcement. Pin the exact commit/build you deploy. Python >=3.12; macOS/Linux service (uses `fcntl`); Web UI in modern browsers. Native Windows service support is not claimed. No stable Python or TypeScript SDK is published. `examples/http_client.py` is an HTTP example, not a new SDK promise.

## Boundaries

Task completion compares existing workspace files against that task's latest immutable publications. Changed outputs must be published before `finish_task` or inferred completion succeeds. Missing drafts retain compatibility with restored publications; unrelated scratch files do not block delivery. Workspace paths escaping the task directory are rejected. This check does not publish edits or certify their content quality.

Task startup and document context recovery list the task's latest publications and unpublished edits, and ask the bot to inspect saved work before editing an older publication. This also applies after resume. It preserves files; it does not automatically publish, merge or approve them.

- **Core:** `runtime/` enforces planning, tools, budget, lifecycle and approvals; `store/` persists immutable artifact revisions, events and execution receipts.
- **Adapters:** `providers/` implements model transports; `api/app.py` validates/authorizes HTTP commands and maps them onto the core. `cli.py` invokes the same service/runtime. Do not reimplement scheduling or permission rules in clients.
- **UI:** renders the persisted state and submits explicit actions. It never declares completion from HTTP acceptance or human adoption. The detailed record remains accessible.

Local mode accepts loopback Host and clients only, with same-origin mutation protection; it is not multiuser authentication. Authenticated deployments require `AGENTTEAM_ACCESS_FILE` and the existing role/run ACL checks. Admin configures; operator needs write access to a run; viewer cannot mutate; auditor has operational read endpoints. Inaccessible runs generally return 404. See `../PRODUCTION.md` and `../../SECURITY.md`. Never expose unauthenticated local mode on a network proxy.

## Wire contract

JSON over HTTP; artifact bytes retain their MIME type. The installed version is `/api/health.version`. Local `/openapi.json` describes request schemas; authenticated deployments disable public schema/docs endpoints. Event envelopes conform to `backend/agentteam/schemas/event.schema.json`. State/event payload additions may occur in this pre-1.0 API: ignore unknown optional properties, display unknown states conservatively, and do not infer success from an unrecognized value. Python internals, generated filenames, admin endpoints and provider-specific options remain experimental.

| Operation | Input / result | Important behavior |
|---|---|---|
| `POST /api/runs` | `goal`, `inputs: {text,urls,files:[{name,content}]}`, optional `budget_usd`, `start` (default true) → 202 run | 202 means accepted. `start:false` does not call a model, but prechecks still run. Failed precheck returns 409 with `run_id`, `status`, `problems`. |
| `GET /api/config` | `execution_summary:[{driver,model,destination,tools}]`, `limits`, `problems` | Summary is available to operators too; contains no credentials, system prompts or URL userinfo/query. Destinations describe effective model configuration, not a network-egress firewall. |
| `GET /api/runs/{id}` | run, tasks, artifacts, approvals, `artifact_selection`, `access`, `last_seq` | Refresh this resource after any command; original receipts are snapshots. |
| `POST /api/runs/{id}/cancel` | → `cancel_requested` | A request to stop is not proof that an in-flight provider call stopped or that sent data was recalled. |
| `POST /api/runs/{id}/resume` | → run | Explicit only. Inspect recorded external effects first; a run must have a resumable plan. No automatic replay after process death. |
| `POST /api/artifacts/{run}/{artifact}/adopt` | `revision >=1`, optional `expected_selected_revision` (0 means none), optional `note` → 202 event/seq | Compare-and-set is serialized in the single-writer service. Stale selection → 409. Repeating the already-current choice with the current expected revision does not append another event. Omitted/null expected revision preserves legacy unconditional behavior. Adoption is a human selection, never a passing check. |
| `GET /api/runs/{id}/export?fmt=zip` | ZIP with latest files | Legacy default preserved. Does **not** mean selected files. |
| `GET /api/runs/{id}/export?fmt=zip&selection=adopted` | ZIP with exactly selected revisions | No selection → 409. Both ZIP modes include `manifest.json` (schema_version 1, run_id, selection, artifact_id/revision/sha256/path), final report, events. Hash-check selected artifact bytes; report/events can also describe newer unselected work. |
| `GET /api/artifacts/{run}/{artifact}/versions/{revision}/raw` | immutable bytes | Verify against the manifest SHA-256. Treat generated HTML as untrusted; the supplied UI uses a sandboxed frame. |
| `POST /api/runs/{id}/instructions` | `text`, `kind`, optional `expected_seq` → 202 `state:received` | Receipt means recorded for the next task session, not that the instruction was executed. Active runs accept directions; interrupted/partial/failed/cancelled/approval-required runs also accept them when they have a plan. Saving never resumes work, rewrites the plan, or reopens completed tasks. Completed/blocked and terminal no-plan runs reject with 409. |
| `GET /api/runs/{id}/events?after_seq=N`, `/stream` | JSON events / SSE | Monotonic per-run `seq`; reconnect with cursor and deduplicate by run/seq. SSE is notification; re-read run detail for authoritative state. |

Artifact IDs are opaque: URL-encode path components. Do not overwrite immutable revisions. Edit a browser-local copy or a downloaded file; edited copies do not inherit the published revision's checks. Ask for a new revision via an instruction while work is active or paused with a plan, or an explicit new request. Publishing a local edited copy as a server revision is not implemented.

## Retry, failure and compatibility

For create/fork/resume, supply `Idempotency-Key` matching `[A-Za-z0-9._-]{8,128}`. The key is scoped to authenticated subject (or local), route and service data directory. Same validated payload returns the original saved response/status, including blocked prechecks; different payload →409. A deleted result →410. Use a new key only for a deliberate new action after resolving the previous outcome.

Both local and authenticated modes persist execution receipts before starting provider work. Durable authenticated mode commits queue intent and receipt together; local mode persists a receipt before launching its process-local task. A local crash between these steps can leave a created run that was never started: a retry returns the receipt and does not launch it. Inspect state and explicitly recover. Creation of the run row and its receipt are not one transaction; a crash before the receipt may leave an orphan unstarted run. This is **not** a general exactly-once guarantee for external systems.

The browser no longer auto-retries mutations. Within the open page, an explicit retry of unchanged create/fork/resume input reuses the key while the response is ambiguous. After reload, inspect recent requests before creating another; request keys are not persisted across page reloads. Drafts/attachments are saved in tab-scoped sessionStorage with in-memory fallback and a warning when storage is unavailable. Do not treat draft persistence as a remote backup.

Errors retain FastAPI's existing shape: `{detail: string|object|validation-array}`, except precheck `{run_id,status,problems}`. 400 invalid key, 401 authentication, 403 authorization/origin, 404 absent/inaccessible, 409 conflict/precheck, 410 deleted receipt, 413 input/export size limit, 422 validation, 429 admission limit (`Retry-After`), 503 unavailable. A transport timeout/5xx can be ambiguous: never silently issue a new command. Keep key and body, inspect state, then decide explicitly. Unknown error payloads must remain visible.

Run states: created/queued/planning/running are not success; approval_required waits for a signed-off action; completed means runtime completion, not guaranteed factual correctness; partial/failed/cancelled/interrupted/blocked retain reasons and existing files. Check records bind artifact ID, revision and SHA-256. A review of an earlier version is not a check of the current one.

Limits: request body 2,000,000 bytes in local mode; UI attachments ≤512KiB each; export files capped at 50MiB (event overhead is additional). Event list/export currently limited by the store's 10,000-event page; large-run export completeness is not guaranteed. Single writer per local data directory; no distributed/shared-filesystem guarantee. Cloud probe and quickstart can make billable calls. Budget figures use configured prices and are not a provider-enforced bill cap. Security headers do not make generated content trustworthy.

## Recovery capabilities (additive, experimental)
`GET /api/runs/{id}` returns `access.can_instruct` from the same Core predicate enforced on POST, combined with write permission. Clients should use it to enable direction controls. `latest_instruction` is the last recorded `instruction.received` event (or null); receipt is not an application acknowledgment. Older servers omit these additions; the bundled UI falls back to the previous active-only behavior.

Resume admission clears the current run's stale `blocked_reason` and `finished_at`; tasks actually reset to queued clear their previous blocked reason. Recorded stop events remain unchanged. Unresolved tasks not reset by resume retain their reasons. Queue receipts agree with the new current state. Saving a correction first avoids racing the start of the next task session; instructions still do not force already accepted work to run again. `expected_seq` is an optimistic check, not a transaction spanning concurrent event writers. Instructions do not have the create/fork/resume idempotency guarantee; after a lost response inspect `latest_instruction`/events before explicitly resending.

When a producer resumes correction work, its saved failing review supplies the findings, summary and previously reviewed artifact revisions if the scheduler's in-memory feedback is absent. This also works after the correction session already consumed that feedback before interruption. The old verdict remains attached to its original bytes; it does not approve the new revision or reopen accepted work.

## Text artifact constraints (experimental, additive)
A requester can include `inputs.delivery_requirements` entries with `logical_path`, `input_format: "text"`, and a JSON Schema such as `{"type":"string","minLength":400,"maxLength":700}`. The runtime validates the whole strict UTF-8 text with JSON Schema draft 2020-12; Unicode code points include Markdown, spaces and newlines. It does not trim, edit or normalize the output. These checks do not prove factual correctness. The Home output-conditions disclosure exposes filename/character bounds without requiring schema knowledge.

Home also offers optional literal phrase exclusions, one per line. They become `not: {anyOf: [{pattern: "..."}]}` within the existing string schema, with regex metacharacters escaped. Matching is case-sensitive anywhere in the whole file, including quotations. API clients can supply the same standard schema; no new server field or validator is introduced. An empty list preserves the previous contract. Exclusions do not infer language or meaning, detect paraphrases, or replace source review. The request draft retains these conditions across reloads.

Text-schema check results include measured `unicode_code_points` and `utf8_bytes` from the exact decoded file. These are measurements, not another model estimate. Default JSON-mode result fields remain unchanged; clients must tolerate additive result fields.

Default/omitted `input_format: "json"` preserves JSON parsing and its previous serialized receipt/evidence hash. Invalid format values return422. Read schema/validation errors in recorded events; unavailable/failed checks cannot be overridden by a model claiming success. A schema-less `run_check(kind=json_schema)` on a published contracted artifact uses the persisted format and schema. Earlier server versions do not enforce text mode; integrations must inspect OpenAPI for this field before relying on it.

## Configuration and model capability evidence
Settings and revision-checked configuration APIs persist to SQLite. After the first start, `agents.yaml` is a mirror of the latest saved revision; editing that mirror does not override SQLite on restart. Use the settings/API to change a running installation.

Every enabled agent's effective model must match its connection's successful probe `model_requested`. Old evidence without that field requires a new probe; a provider's alias-normalized `model_reported` is not substituted. A model change cannot reuse another model's probe. Current configuration stores one probe per connection: configure separate connection IDs when using different models against the same endpoint. Precheck reports `capability_model` with the affected agent and stops before model execution. CLI quickstart and benchmark tools re-probe a changed model; cloud probes are real potentially billable calls.

## Document workflow (experimental, opt-in)
`inputs.workflow: "document"` selects a Core-compiled two-task plan: an enabled builder receives the unchanged request and produces the declared text file; a separate enabled reviewer checks the exact revision against the original request, source and delivery contract. It skips the model planning call and optional milestone/exception replanning, not generation or review. Normal bounded reviewer-requested corrections still apply. The document reviewer can read inputs and published files, run registered file checks, exchange findings and submit reviews; it cannot write/publish replacement files or run shell commands. This restriction is enforced by the gateway even if the general agent configuration includes those tools. General team-workflow review permissions are unchanged. New document plans independently check delivery format, language, original-request fulfillment and source accuracy. Requires supplied text or attachments, no URL inputs, and exactly one text delivery requirement; invalid inputs return422. Missing roles or insufficient task limits fail explicitly. It is a document workflow, not a general research/task planner or network isolation guarantee. Existing tool/permission policy still applies.

Default/omitted workflow `"team"` retains the existing configurable planning behavior and serialized request hashes. Home offers an explicit checkbox next to output conditions; it persists with the draft and is cleared on discard. Old servers do not implement this option; inspect OpenAPI before using it.

## Review revision binding
`submit_review` must reference the exact latest published artifact set owned by its target task. Unknown, older, foreign-task, duplicate, incomplete or SHA-mismatched references are rejected. Omitting references retains the previous behavior of binding the latest set at submission. Scheduler checks again immediately before acceptance; if bytes/versions changed after submission, both producer and review task become partial and require a new review. Historical review events are preserved. This validates the review target, not the truth of a model's semantic verdict.

For the single-document text workflow, the advertised `workspace_write` content schema repeats top-level requester `minLength`/`maxLength` bounds. This is a model-generation hint, not a replacement for saved-byte checks. Full requester schemas remain authoritative in Core; arbitrary schemas are not transplanted into nested tool arguments because that could change `$ref` resolution. Ollama generation uses explicit connection sampling values when supplied; otherwise its OpenAI-compatible endpoint controls the defaults. Capability probes alone force temperature 0.

## Conversation voice configuration

`PATCH /api/agents/{id}` accepts optional `speech_style` (at most600 Unicode characters) with the existing expected_revision contract. Empty string restores the role default; omitted/null leaves the setting unchanged. Create-agent accepts the same optional field. It is a pre-1.0 config extension, removed from legacy blueprint validation. The effective style is stored separately from the editable role prompt and frozen with the run snapshot. UI/CLI/task workers/planning/reporting share the Core configuration. Style does not grant tools or waive review.

Normal team runs now include a coordinator handoff session after task persistence and before worker scheduling. The model sends real messages through the existing gateway; all task owners must have a persisted handoff/decision before this session can finish. Configured tools and run budgets still apply. Existing persisted deliveries are reused on resume; this is local message recovery, not a broker/external-operation exactly-once guarantee. Document and single-agent flows remain unchanged. This may require additional model calls within the same configured limits.

Conversation voice is also supplied as a per-agent description of `send_message.text` in the model's tool schema. It is a generation hint, not a validator or a post-processing rewrite: the saved message remains the model's actual output. Tool permissions and message fields are unchanged, and schemas are copied so one teammate's voice does not leak into another's. Validate the actual conversation separately from configuration persistence.

For the normal LLM loop (including Ollama), the runtime ends the dispatch session once all required deliveries are confirmed in the database, without requiring an extra model acknowledgement. This only completes dispatch: it does not certify message content, recipient understanding, production tasks, or artifact reviews. The CLI session path does not use this optimization. The current delivery requirement is one message per task owner, not one message per task.

When read_artifact or send_message references omit a filename extension, a failed exact lookup may suggest matching stems from the current run. The error includes full IDs and available revisions; it never selects a candidate, reads artifact bytes, or sends a message automatically. Callers must retry deliberately with the complete identifier.

Plan validation reuses the workspace write-path policy. An absolute or escaping output path is rejected before dispatch, rather than assigning a task whose declared output cannot be published. Existing runtime write checks remain authoritative.

Message artifact_refs refer only to published revisions starting at 1. Original attachments and planned outputs are named in message text with artifact_refs omitted. Coordinator dispatch explains that original inputs are passed to the workers; this does not grant the coordinator additional read permissions.

Ollama sampling extensions (experimental): connection YAML/PUT supports `ollama_temperature` (finite 0–2) and `ollama_top_p` (finite >0–1). PUT omission preserves the saved value; explicit null clears it. Both are sent only for the ollama driver, and changing the connection resets probe status. They are captured in new-run configuration snapshots; running jobs retain their original configuration. The blueprint schema remains unchanged, as with ollama_thinking. Other drivers are unaffected. In Ollama 0.33.3, omitted OpenAI request temperature/top_p become 1.0 even when a Modelfile differs; see [the versioned adapter implementation](https://github.com/ollama/ollama/blob/v0.33.3/openai/openai.go).

Literal/structural run_check replies (text_contains, text_not_contains, regex_count, markdown_basic) include additive interpretation guidance. Their status, findings, target revision/hash and check.completed evidence are unchanged. A keyword match proves text presence, not whether an action happened. Explicit requester constraints remain mandatory; semantic review must compare actual claims with sources.


### Bounded document context recovery
When a task response reaches the output limit without a tool call, document-only tool sets can rebuild the conversation from saved task/source/instruction/inbox state, existing published outputs and sent messages. This also applies without a requester JSON Schema. The first two consecutive no-tool responses may recover; the third follows the existing termination and delivery/review guards. Counters, permissions, artifacts and task status are not reset. Newly added tools are excluded unless explicitly classified as reconstructable. Existing schema-based recovery remains compatible.

This is not full conversation replay: older inbox/sent entries are bounded to 20, unsaved generation is not an artifact, and arbitrary external tool effects are not reconstructed. The newly expanded path excludes execution, external mutation and task-management tools, and excludes a task if its recorded calls include `run_check(kind=command)` (even a failed/denied call). Tool names alone do not imply absence of shell effects. Current live sessions keep their loaded code; passing recorded-state tests does not establish improved live-model completion.

Conversation tool hints use the configured voice and suggest concise, role-specific handoffs. They do not rewrite saved messages, cap their length, invent findings, or override a user's requested form. Detailed review findings belong in submit_review; a chat finding does not satisfy the review gate, including on a failing artifact. These are model instructions, not a guarantee of personality fidelity.

Review tool schemas now suggest the task's declared review target IDs and existing acceptance IDs. With one target, result-count bounds mirror its criterion count. The execution layer still checks the chosen target, exact criterion coverage, duplicates, and current artifact revisions. Multiple targets use a union of IDs as a provider hint; it does not replace target-specific validation. Shared/global schemas remain unchanged.

After a reviewer has submitted a verdict but ends without a tool call, the same bounded document-context recovery can restore its in-session review records and show the remaining post-review handoff recipients. It does not submit, send, accept, or finish anything. A pre-review message is still insufficient: the existing submit_review/finish_task handoff guard remains authoritative. This recovery is limited to the first two consecutive no-tool turns and the existing reconstructable-task checks.

Task prompts label master assumptions as provisional rather than verified facts or additional permission. Workers retain the exact recorded assumptions but must check them against the original request and inputs; an upstream message cannot expand a design request into implementation or external execution. This is model guidance, not semantic validation or an additional authorization mechanism. The existing tool policy remains authoritative.

Publication replies and missing-handoff errors explain the existing handoff invalidation rules: a new publication clears earlier handoffs, and submit_review clears the handoff to its target owner. Complete publication first, then deliver current artifact references. Reading the inbox is not a delivery. These response hints do not send messages, modify recipients, reset budgets, or bypass finish_task validation.

If workspace_read cannot find a local file, it can point to an exact published artifact ID/revision in the same run when the caller already has read_artifact permission. This does not read the artifact, create an artifact.read event, copy it into the workspace, or bypass workspace path validation. Existing local files take precedence. A missing file in one task workspace is not proof that another task never published it.

## Adaptive teams (experimental)

`inputs.team_selection: "adaptive"` asks the configured coordinator to recommend 1–6 specialists (also bounded by `max_tasks`) before planning. The coordinator is additional. The normal Web request defaults to this option; unchecking it uses the configured team. Existing HTTP/CLI inputs that omit the field retain `fixed` behavior. Explicit single-agent and document workflows retain their existing team formation.

Generated specialists copy enabled agent templates. Internal roles are permission/review classes, not a fixed list of professions. `specialty`, personal name, emoji and `speech_style` describe the person; tools, model, connection, skill permissions and budget are inherited. Locked bot settings are preserved. The coordinator's recommendation is saved in the run snapshot and emitted as `team.selected`; rejected proposals emit `team.rejected`. A failed recommendation does not silently fall back to four people. Resume restores the selected configuration. A recommendation is not a completed task or proof of professional qualifications.

New recommendations request temperament and concrete conversational style separately, then store both in the existing `speech_style` profile. Earlier saved recommendations without the separate style remain readable. This guides model speech; messages are not rewritten after delivery, and distinct voices still require observation in an actual run.

Adaptive planning also checks a conservative reservation for compulsory communication before accepting a new plan: one coordinator delivery per task, the distinct recipients derived from task dependencies, and configured correction/review rounds. Reviewer reservations account for targets being corrected in separate rounds. An insufficient per-task limit rejects the proposed plan; the runtime does not increase configured limits. This is an admission check, not a guarantee against optional messages exhausting capacity. Existing saved runs and fixed-team planning are unchanged.

Newly admitted adaptive plans persist `config_snapshot.communication_budget_version: 1`. Only that version reserves future compulsory handoffs at send time; older saved runs retain their previous reservation behavior. Pending question replies reserve one additional message until an answer matches `reply_to` and both endpoints. All peer deliveries, including reply sessions, now count toward the lifetime task limit, matching reconstruction from stored messages on resume. This closes previously uncounted replies and may reject replies earlier than older runtime versions did. Reservations are conservative; they do not prove model correctness or guarantee completion after arbitrary plan changes.
