# Agent Team SNS投稿草案

## 前提

- 製品: Agent Team。一度の依頼から AI チーム（Master / Researcher / Builder / Reviewer）が実際に作業し、成果物・Bot 間の実メッセージ・時系列を同じ実行記録から表示する、オープンソースのローカルファーストなツール。
- 対象読者: ソフトウェア開発者・個人開発者。
- トーン: 日本語、常体まじりの落ち着いた調子。誇大表現は使わない。
- 価格は未定のため、金額・課金形態・プランに関する表記は一切置かない。
- 提供テキストにない実績値（ユーザー数、処理速度、精度、導入企業、受賞など）は書かない。
- 実 URL は与えられていないため、リンクはすべて `{{REPO_URL}}` などのプレースホルダで表記する。差し替え前に投稿しない。
- 3 案は同一文の言い換えではなく、媒体・長さ・訴求軸を変えて書き分ける。

## 案B

### 本文（開発者コミュニティ向け・中尺）

```
Agent Team という OSS のローカルファーストなツールを作っている。

やっていることは単純で、ひとつの依頼を受け取ると Master / Researcher / Builder / Reviewer の4役が
それぞれの担当範囲で実際に作業し、その過程をひとつの実行記録に残す。

この手のマルチエージェント構成でいつも気になるのが「本当に各役が仕事をしたのか」という点だった。
最終出力だけ見せられても、途中で何が起きたのかは分からない。

Agent Team は次の3つを同じ実行記録から表示する。

- 成果物: Builder が実際に書き出したファイル
- Bot 間メッセージ: Master / Researcher / Builder / Reviewer が実際にやりとりした本文
- 時系列: どの役が、いつ、何をしたか

要約ではなく実行時のデータをそのまま出すので、期待どおりに動かなかったときに
どこで判断がずれたのかを自分で追える。Reviewer の指摘と Builder の修正が
同じ時系列上に並ぶため、レビューが形だけになっていないかも確認できる。

ローカルファーストにしたのは、依頼内容と生成物を手元に置いたまま試したかったから。
オープンソースなので、役割の定義やプロンプトの中身も読んで変えられる。

まだ荒い部分があるので、実際に動かして「ここは設計として無理がある」という指摘をもらえると助かる。

{{REPO_URL}}
```

- 想定媒体: 開発者コミュニティ（Reddit の技術系サブレディット、技術系フォーラム、開発者向け Slack / Discord の共有チャンネル）
- 長さの目安: 600〜800字。冒頭2行で概要が分かる構成にし、詳細は箇条書きに逃がす。
- ハッシュタグ案: `#OSS` `#マルチエージェント` `#ローカルファースト` `#開発ツール`（タグ文化のない媒体では省略し、代わりにフレアやカテゴリを使う）
- 想定CTA: リポジトリで実装を確認し、フィードバックを Issue に書く → `{{REPO_URL}}` / Issue は `{{ISSUES_URL}}`
- 補足: コミュニティによっては自己プロモーションの投稿規約があるため、投稿前に各コミュニティのルールを確認する。

## 案C

### 本文（note / LinkedIn 向け・長め）

```
AI エージェントの出力を、もう一度自分で検証できるようにしたかった

AI にまとまった作業を任せると、返ってくるのはたいてい最終成果物だけだ。
出来がよければそれでいい。問題は、期待とずれたときに手がかりが残らないことだった。
どの段階で解釈が変わったのか、調査が足りなかったのか、実装が仕様を取り違えたのか。
結果だけを見て原因を推測するのは、ログのないバグ調査に似ている。

Agent Team は、その手がかりを残すために作ったオープンソースのツールだ。

■ 一度の依頼から、4つの役が動く

依頼をひとつ渡すと、次の4役がそれぞれの担当で作業する。

- Master: 依頼を読み、前提を整理し、作業を分けて割り当てる
- Researcher: 必要な情報を集め、根拠と一緒に整理する
- Builder: 実際にファイルを作る
- Reviewer: 成果物を確かめ、直すべき点を返す

役割を分けること自体は珍しくない。Agent Team が重視したのは、
分けた結果として何が起きたかを、あとから同じ場所で読めるようにすることだった。

■ 成果物・メッセージ・時系列を、同じ実行記録から見る

Agent Team は、ひとつの実行について次の3つを同じ実行記録から表示する。

1. 成果物: Builder が実際に書き出したファイル
2. Bot 間の実メッセージ: 4役が実際に交わしたやりとりの本文
3. 時系列: どの役が、いつ、何をしたかの並び

要約された作業ログではなく、実行時のデータをそのまま見る。
Reviewer が何を指摘し、Builder がそれをどう反映したのか。
Researcher が渡した情報が、成果物のどこに効いているのか。
そうした対応関係を、自分の目で確かめられる状態にしておきたかった。

■ ローカルファーストと、オープンソースであること

依頼内容にも生成物にも、外に出しにくいものが混じる。
だから、手元で動かして手元にデータが残る形を選んだ。

オープンソースにしたのも同じ理由に近い。
役割の定義や進行のルールが読めなければ、出てきた結果を評価しようがない。
中身を読んで、自分の使い方に合わせて変えられることを前提にしている。

■ 想定している使い方

- 調べもの、下書き、検証を一続きの作業としてまとめて任せたいとき
- ひとりで開発していて、レビュー役が欲しいとき
- エージェントの構成そのものを自分で作り替えたいとき

■ これから

まだ整えている途中で、粗い部分も残っている。
実際に動かしたうえでの指摘が、いまいちばん役に立つ。

詳細とソースコードはこちら: {{REPO_URL}}
```

- 想定媒体: note（見出し記号 ■ をそのまま利用）/ LinkedIn（見出し記号を外し、段落間を1行空けに整える）
- 長さの目安: 1,200〜1,500字。読み物として成立させるため、冒頭に「何を解決したかったか」を置く。
- ハッシュタグ案: note → `#OSS` `#個人開発` `#AIエージェント` `#開発ツール` / LinkedIn → `#OpenSource` `#DeveloperTools` `#AIAgents`
- 想定CTA: 記事末尾でリポジトリへ誘導 → `{{REPO_URL}}`
- 補足: LinkedIn では冒頭3行が折りたたみ前に表示されるため、1〜3行目だけで趣旨が伝わるかを投稿前に確認する。

## 補足

- 本草案は未公開ドラフトであり、投稿は行っていない。外部送信・公開・配信は一切実施していない。
- `{{REPO_URL}}` `{{ISSUES_URL}}` はプレースホルダである。実 URL が確定するまで投稿しない。
- 価格は未定のため、いずれの案にも金額・課金形態・プランの記載を置いていない。触れる必要が生じた場合は「価格は未定」の一文のみとする。
- ユーザー数、処理速度、精度、導入事例などの実績値は未確認のため記載していない。数値を入れる場合は、根拠のある実測値に差し替える。
- スクリーンショットやデモ動画は未提供のため、添付案は「取得後に差し替え」として保留している。
- 投稿前チェック: (1) プレースホルダの差し替え漏れがないか、(2) 媒体ごとの文字数制限に収まるか、(3) 各コミュニティの宣伝ルールに反しないか。
