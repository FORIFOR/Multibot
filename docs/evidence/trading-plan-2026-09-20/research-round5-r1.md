## 1. 注文の識別と照会（公式仕様）

### 注文 ID の生成
- 注文には `client_order_id` またはサービス側 ID が使用可能。
- `client_order_id` を指定しない場合、サービス側で ID が生成される。
- 成行注文の約定価格は変動し得る。指値注文は約定が保証されない。

### 照会方法
- どちらの ID（client_order_id またはサービス側 ID）でも状態照会が可能。
- オープン注文の更新は WebSocket ストリームで受信できる。

### 技術的制約
- 任意の HTTP 再送が安全だという保証はない。
- 重複防止のため、サーバーサイドの idempotency キーとクライアント側の `client_order_id` 管理の組み合わせが必要。

## 2. 注文更新（WebSocket ストリーミング）

### ストリームイベントの定義
- 認証後に `trade_updates` を購読。
- イベント種類:
  - `new`: 新規注文
  - `partial_fill`: 部分約定
  - `fill`: 完全約定
  - `canceled`: 取消
  - `rejected`: 拒否
  - `pending_cancel`: 取消待ち（取消完了ではない）

### 注文状態の同期
- 注文状態は受信イベントの `order` オブジェクトにも含まれる。
- Paper の注文ストリームと市場データストリームではフレームの扱いが異なる。

### 技術的制約
- 応答喪失時の再接続ロジック（exponential backoff）を実装必須。
- 再接続後に、口座・注文・約定を照合する必要がある。

## 3. Paper と Live（公式仕様）

### 接続の違い
- Paper と Live は API キーと接続先が異なる。
- Paper は実市場と同じ約定品質の証拠ではない。

### 機能の違い
- 公式資料によると、Paper では：
  - 配当を模擬しない
  - 注文数量を実際の NBBO 数量と照合しない
  - 本番の収益性や流動性の保証ではない

### 実装段階
- 発注前に、口座・銘柄・売買・数量・価格条件・推定費用・live/paper を確認する。
- ブラウザーへ証券 API の秘密鍵を渡さない。
