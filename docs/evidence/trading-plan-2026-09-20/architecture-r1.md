## 1. 概要

本ドキュメントは、証券 API を活用した株式トレードアプリのシステムアーキテクチャを定義します。対象市場・証券会社・認証方式是未確定のため、汎用的なアダプターパターン（Adapter Pattern）を採用し、市場固有ロジックをモジュール化する設計としています。

**重要な前提**: 本検討中は、実際の口座への接続・発注は行いません。全ての設計は Paper 取引環境での検証を前提とし、Live 移行前の段階を明確に区別します。

## 2. システム境界とコンポーネント定義

### 2.1 コア層 (Core)

Core はシステム全体の状態管理と、証券アダプターとの通信制御を行います。

└─────────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────────┐

### 2.2 コンポーネント説明

#### 2.2.1 Core 層コンポーネント

1.  **OrderManager**: 
    - 注文の送信・取消・状態照会を管理
    - サーバー側での状態管理を担当
    - 重複防止ID（idempotency key）の付与

2.  **StateSync**: 
    - 注文状態の同期（サーバーとクライアント間）
    - イベント（trade_updates）の受信用
    - 部分約定・取消状態の追跡

3.  **ReconnectHandler**:
    - 通信切断時の再接続制御
    - Exponential Backoff + Jitter の適用
    - 再接続後の状態照合（口座・注文・約定）
    - **通信失敗を「未発注」として新規送信する代わりに、元の注文IDで照合する**

4.  **PriceCache**: 
    - 価格データのキャッシュ管理
    - 取得時刻・権限の記録
    - 「リアルタイム」は取得時刻を表示

5.  **AuthStore**:
    - 認証トークンの管理（サーバー側に保存）
    - OAuth2/JWT フローの実装候補
    - クライアントへの秘密鍵渡さない設計

6.  **LiveStatus**: 
    - Paper/Live 状態の切り替え管理
    - 移行条件の検証

#### 2.2.2 証券アダプター層

各市場・証券会社ごとに実装したアダプターを提供。コア層はアダプターを介して市場と通信します。

- **Adapter Interface**: 
  - `initialize()`: アダプターの初期化
  - `fetch_account()`: 口座情報の取得
  - `create_order()`: 注文送信
  - `cancel_order()`: 注文取消
  - `fetch_orders()`: 注文状態照会
  - `subscribe_stream()`: トレード更新ストリームの購読

- **AdapterFactory**: 既存の API クライアントをラップし、汎用的インターフェースへマッピング

#### 2.2.3 UI 層

- クライアント側の認証・認可は JWT の検証のみ
- 秘密情報はクライアントに保存せず、認証状態を UI で反映
- 価格表示は取得時刻を明記

## 4. 異常時処理

### 4.1 再接続処理

通信接続が失われた場合:

1. 再接接続を開始（Exponential Backoff + Jitter）
2. 再接続成功后、以下の照合を行う:
   - 現在の口座残高
   - 未承認の注文（pending）
   - 部分約定中の注文
   - サーバー上の最新の注文状態
3. クライアントとサーバーの状態整合性を確認
4. 照合された結果を UI に反映

### 4.2 重複防止

- 発注要求の永続化：`idempotency-key` の付与
- 結果不明の場合：元の注文IDで照会し、サーバーの状態を確認
- 新規注文送信は行わず、サーバーの回答を待つ

### 4.3 部分約定・取消競合

- サーバー側での順序制御：注文イベントの順序を保持
- クライアント側の再開ロジック：部分約定後の状態を UI に反映

### 4.4 プライベート接続制限

- CORS 制限：ドメイン指定のみ許可
- 価格リアルタイム性：取得時刻を表示し、古い価格を「リアルタイム」と称しない

## 5. リスク管理

- **市場未定義リスク**: 対象市場・証券会社は未定。設計拡張性を考慮
- **認証未検証**: OAuth2/JWT が候補だが、最終認証方式未確定
- **法適合性**: 税務・法令は未検証。市場ごとの規制を調査
