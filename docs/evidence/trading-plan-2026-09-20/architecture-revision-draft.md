# 株式トレードアプリ アーキテクチャ設計

## 1. システム全体概要

本システムは、株式トレードアプリで、Core、証券 Adapter、UI の 3 層構成とする。
- **Core**: 注文状態管理、状態機械、重複防止、エラーハンドリングの中枢
- **証券 Adapter**: 各証券会社の API へ接続し、注文・市場データ・口座情報を抽象化
- **UI**: ユーザー向け画面、価格取得時刻・利用権限表示

## 2. 境界線

### Core ↔ 証券 Adapter
- 証券 Adapter は Core へ `Order`, `OrderStatus`, `MarketData` を提供
- **`client_order_id` 管理**:
  - クライアント: 発注前に生成し、発注要求ヘッダーに含める
  - サーバー (Core): 受信した `client_order_id` を永続化（DB/ストレージ）
  - 再送時: サーバーが `client_order_id` で照会し、結果照合を行う
  - 永続化対象: `client_order_id`, 発注時刻、発注内容、最終状態、証券側 order_id
- 状態機械は Core が維持し、UI へ状態を通知

### Core ↔ UI
- Core は WebSocket 接続を管理し、UI へ `trade_update` をストリーミング
- UI は価格取得時刻（2 種類）と利用権限を表示
- UI へ送信する `trade_update` は、`server_timestamp` と `client_receive_timestamp` を含む

### 証券 Adapter ↔ 外部 API
- 認証は OAuth2 または API キーペア
- 秘密鍵はサーバー側管理（サーバーサイドでトークン検証後、証券 API キーを介して注文を処理）
- Paper/Live 接続先は Adapter 設定で切り替え

## 3. 画面構成

### 主要画面
- 口座情報画面（Live/Paper 切り替え、残高、利用権限）
- 注文画面（銘柄、数量、注文タイプ、価格条件）
- 約定履歴画面（部分約定・完全約定・取消）
- 市場データ画面（取得時刻付き）

### 利用権限表示
- 画面に「利用権限: あり/なし」を表示
- 権限確認結果はサーバーが検証し、UI へ通知

### 価格時刻表示
- 市場データには 2 つの時刻を表示:
  - `取得元時刻 (server_timestamp)`: WebSocket サーバー時刻（元データ時刻）
  - `画面受信時刻 (client_receive_timestamp)`: クライアント受信時刻
- 古い価格（`client_receive_timestamp` が古い）を「リアルタイム」と称さない

## 4. 認証認可

### 利用者認証と証券 API キーの分離
- **利用者認証**: OAuth2 または API キーペア（アプリ利用者の認証）
- **証券 API キー**: サーバー側管理（証券会社へのアクセス用）
- **認可フロー**:
  1. ユーザーがアプリへログイン（OAuth2 または API キー）
  2. サーバーがユーザー認証トークンを検証
  3. ユーザーが「口座操作許可」を承認
  4. サーバーが許可されたユーザーの証券 API キーで注文を処理
  5. ブラウザへ証券 API の秘密鍵は渡さない

### 認可の境界
- 利用者認証トークン ≠ 証券 API キー
- サーバーがユーザー認証トークンで証券 API キーを保護
- 認可はサーバー側で管理し、UI へ「利用可能/不可」を通知

## 5. 注文状態管理

### 状態機械 (Finite State Machine)

| 状態 | 遷移条件 | 説明 |
|------|----------|------|
| `pending` | 新規発注、部分約定、完全約定、拒否、取消 | 発注直後 |
| `partial_fill` | 部分約定後、残数量完全約定、残数量取消 | 部分約定中 |
| `fill` | 部分約定せず完全約定、部分約定後残数量完全約定 | 完全約定 |
| `rejected` | 証券側で拒否 | 拒否 |
| `canceled` | 取消完了、部分約定後の残数量取消 | 取消完了 |
| `pending_cancel` | 取消要求中 | 取消待ち（取消完了ではない） |

#### 遷移条件の詳細

- **部分約定せず全約定/拒否される場合**:
  - `pending` → `fill` (完全約定) または `pending` → `rejected` (拒否)
  - 部分約定イベントを受信しない場合

- **取消待ち中の約定**:
  - `pending_cancel` 中に market data が入る可能性あり（価格変動）
  - 取消完了前に約定イベントを受信した場合、`pending_cancel` → `fill` または `canceled`
  - 取消完了後、市場データが来ても無視

- **部分約定後の残数量取消**:
  - `partial_fill` → `canceled` (残数量取消)
  - 残数量の取消要求が完了した時点で遷移

### 重複防止
- **サーバーサイド**: idempotency key（`client_order_id` を使用）
- **クライアント側**: `client_order_id` 管理（発注前に生成）
- **再送時の重複防止**: サーバーが `client_order_id` で照会し、結果を返す

## 6. エラーハンドリング

### 応答喪失時の再接続

#### 再接続ロジック (exponential backoff)
- 接続切断時: `backoff_time = base_delay * 2 ^ attempt_count`
- `base_delay`: 1 秒、`attempt_count`: 0, 1, 2, ...
- 最大再試行回数: 10 回

#### 再接続後の照合順序と条件
1. WebSocket 接続を確立
2. 認証リクエストを送信
3. `trade_updates` ストリームを再接続
4. 直近の `order` 状態を照会（`client_order_id` で照会）
5. 照合項目:
   - 口座残高
   - 注文状態（`client_order_id` で照会）
   - 約定状態（`client_order_id` で照会）
6. 結果を UI へ通知

#### エラー分類
- **一時的エラー**: 再試行（exponential backoff）
- **永続的エラー**: UI へエラー表示、ログ出力

## 7. 発注前の確認フロー

発注前に以下の項目を確認する。

### 確認項目
1. **口座**: 有効な口座が選択されているか
2. **銘柄**: 取引可能な銘柄か（上場済み、取引時間内）
3. **売買**: 売買権限があるか
4. **数量**: 口座残高以内か
5. **価格条件**: 指値価格が妥当か（成行は価格なし）
6. **推定費用**: 手数料・税金の推定
7. **環境**: Paper/Live の切り替え

### 確認フロー
1. ユーザーが注文画面へ移動
2. 確認ダイアログを表示（確認項目を列挙）
3. ユーザーが「確認した」を選択
4. サーバーが各項目を検証
5. 検証失敗: エラーメッセージを表示
6. 検証成功: 発注へ進む

## 8. Live 通過条件

本番接続への通過条件を定義する。

### 通過条件
1. **API キー検証**: 証券会社の API キーが有効か
2. **Paper→Live 切り替えテスト**: 接続先を切り替えて正常動作か
3. **注文テスト**: Paper/Live 両方で注文が正常に処理されるか
4. **権限確認**: 取引権限があるか
5. **検証通過**: 上記全項目が正常に動作

### 通過後の手順
- 通過条件を満たすと、Live 環境での取引が可能
- 権限確認・検証通過後の本番接続を開始

## 9. 実装順序

1. **Paper 環境での実装**
   - WebSocket 接続の確立と再接続ロジック
   - 注文フローのテスト
   - 状態同期の検証
   - 発注前確認フローの実装
   - 発注テスト

2. **Live 環境への拡張**
   - API キーの切り替え
   - 本番接続のテスト
   - 本番取引の開始（権限確認・検証通過後）
   - Live 通過条件の検証

## 10. 検証条件

- 状態機械の遷移が正しく動作すること
- 再接続ロジックが適切に動作すること
- 重複防止が機能すること
- 価格時刻（2 種類）が表示されていること
- 発注前確認フローが機能すること
- Live 通過条件が満たされること
