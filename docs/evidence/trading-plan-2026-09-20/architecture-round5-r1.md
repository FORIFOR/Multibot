# 株式トレードアプリ アーキテクチャ設計

## 1. システム全体概要

本システムは、株式トレードアプリで、Core、証券 Adapter、UI の 3 層構成とする。
- **Core**: 注文状態管理、状態機械、重複防止、エラーハンドリングの中枢
- **証券 Adapter**: 各証券会社の API へ接続し、注文・市場データ・口座情報を抽象化
- **UI**: ユーザー向け画面、価格取得時刻・利用権限表示

## 2. 境界線

### Core ↔ 証券 Adapter
- 証券 Adapter は Core へ `Order`, `OrderStatus`, `MarketData` を提供
- 証券 Adapter 側は `client_order_id` 管理、idempotency key 生成を担当
- Core は状態機械を維持し、UI へ状態を通知

### Core ↔ UI
- Core は WebSocket 接続を管理し、UI へ `trade_update` をストリーミング
- UI は価格取得時刻を付与し、利用権限を表示

### 証券 Adapter ↔ 外部 API
- 認証は OAuth2 または API キーペア
- 秘密鍵はブラウザへ渡さない
- Paper/Live 接続先は Adapter 設定で切り替え

## 3. 画面構成

### 主要画面
- 口座情報画面（Live/Paper 切り替え、残高、利用権限）
- 注文画面（銘柄、数量、注文タイプ、価格条件）
- 約定履歴画面（部分約定・完全約定・取消）
- 市場データ画面（取得時刻付き）

### 利用権限表示
- 画面に「利用権限: あり/なし」を表示
- 価格取得時刻を「取得時刻: YYYY-MM-DD HH:mm:ss」で表示

## 4. 認証認可

- ユーザー認証: OAuth2 または API キーペア
- 証券 API キーはサーバー側管理
- ブラウザへ秘密鍵を渡さない

## 5. 注文状態管理

### 状態機械 (Finite State Machine)
- 状態: `pending` → `partial_fill` → `fill` / `canceled` / `rejected`
- `pending_cancel`: 取消待ち（取消完了ではない）
- 部分約定と取消競合は状態機械で管理し、UI と同期

### 重複防止
- サーバーサイド: idempotency key
- クライアント側: `client_order_id` 管理
- 再送時の重複防止

## 6. エラーハンドリング

### 応答喪失時の再接続
- Exponential backoff を使用
- 再接続後に、口座・注文・約定を照合

### エラー分類
- 一時的エラー: 再試行
- 永続的エラー: UI へエラー表示、ログ出力

## 7. 実装順序

1. **Paper 環境での実装**
   - WebSocket 接続の確立と再接続ロジック
   - 注文フローのテスト
   - 状態同期の検証

2. **Live 環境への拡張**
   - API キーの切り替え
   - 本番接続のテスト
   - 本番取引の開始（権限確認・検証通過後）

## 8. 検証条件

- 状態機械の遷移が正しく動作すること
- 再接続ロジックが適切に動作すること
- 重複防止が機能すること
- 利用権限表示が正確であること
