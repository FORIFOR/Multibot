# Workroom 最終候補の独立レビュー

対象は既存 Paper ブランドの Workroom。設計基準は `docs/design/AWARD_QUALITY.md`、初見課題は「成果物を読む→確認記録を理解する→使う版を選ぶ→採用版を保存する」。AI が既存コードと記録を知る立場で行った独立レビューであり、人間の初見試験や受賞審査ではない。アプリ実装を編集していない。

## 結果

見た範囲の UI と主要操作について、旧 P2（確認記録を開いた後のキーボード位置の不一致）は解消。読取・採用・保存の順序が改善し、新しい P1/P2 の UI 指摘はなかった。別途、サービス終了後の stderr で監査保存の `database is locked` が担当者から報告され、原因調査中。下記の操作通過を全リクエスト無エラー・サービス受入と扱わない。

### Before → after

- 旧版は本文より上に赤い採用、最新ZIP、別タブ、編集、修正依頼が並び、読む前に採用へ誘導する構図だった。最終候補は `01 読む`→`02 確認の記録を読む`→`03 使う版を選ぶ`、続いて採用ZIP。原文/別タブ以外の補助操作は本文後の開閉欄へ移った。
- ファイル名・現在の版・採用状態を本文前で読める。1件だけのファイル選択ボタンと同名見出しの重複はなくなった。複数ファイル時の UI はコード上維持するが、今回の実記録では未操作。
- 旧版の実 Tab→Enter は確認記録を展開/スクロールするだけで focus が元ボタンに残り、次の Tab は採用だった。最終候補では summary に focus が移り、画面内に 3px の枠を表示する。採用済みなら次の Tab は採用ZIP、未採用なら採用操作へ進む。
- 「採用した版と作業記録の ZIP」と「採用状況にかかわらず各ファイルの最新版と作業記録の ZIP」を別の位置/説明で区別できる。採用が正確さの保証でないこと、チェックが表示版に対する記録であることも常設されている。

## 実施した操作と証拠

元 v62 の実記録を別担当が私有 SQLite に移した環境を使用。秘密キーは発行済み file 参照だけで入力。固定配布ファイルは `index-DkBnZueV.js`、SHA は `verification.json`。HTTP を差し替えず、追加 LLM/probe/模擬データなし。

1. baseline rep3: Chrome 154.0.8037.58 で上記 focus 不一致を再現。私有copy上で実採用/ZIP/reload保持を確認（`../independent-baseline-r1/baseline-verification.json`）。
2. final rep3: JA 1440/390/320、EN390 の4条件で、現在版表示・重複ボタンなし・本文/確認/採用/保存の順序、実 Tab/Enter のfocus移動を確認。document.scrollWidth は viewport と一致した。採用済み版はキーボードだけで ZIP 保存できた（`observations.json`）。
3. final rep4: 390px の未採用実記録で Tab→確認記録→summary→Tab採用→Enter→chosen-pill→Tab保存→Enterダウンロード→reload選択保持を確認（`rep4-adoption.json`）。追加イベントは `artifact.adopted` 1件のみ。AIが私有copyで選んだ事実で、人間の受入を意味しない。
4. rep3/4 の ZIP は全entry集合、選択 revision/SHA、readiness.json と final-report.md の全bytes SHAを原資料と照合した。49参照ファイル不変、queued/leased0、追加modelイベント0（`verification.json`）。
5. 別担当の最終候補の実 native200%画像3枚（inner720/outer1440/DPR2/CSSzoom1）を独立に開いて目視。読む/確認/保存の文字と主要操作に欠けは見つからなかった。ズーム実操作と測定は別担当、このレビュー担当は画像を確認した。
6. 別担当の EN390 failed / EN320 interrupted 画像も目視。全体未完了と途中成果の注記を本文前に維持し、対象版の記録されたチェック通過と区別している。旧AI発言や成果物本文を正しい文へ書き換えていない。

所有 Chrome は終了。API の終了・原DBを含む最終保全は担当者の `../cleanup.json` を参照。私自身の SQLite は mode=ro の SELECT/PRAGMA、明示BEGINや書込なし。独立 Chrome の主要操作は通過したが全 HTTP response 監視は行っておらず、500ゼロを主張しない。baseline補足の最初の2回のSQLite読取は検証側のテーブル/列名誤記で中断し、実schema確認後の読取へ訂正した。製品変更やデータ書込はない。

## 残る点・範囲

P3: 小画面の初期表示では、本文の開始は document Y=882.6px（390幅）、956.2px（320幅）にあり、最初のviewportより下。依頼情報・チーム表示をもう少し短くし、本文へ早く到達できる余地は残る。主要操作を妨げる新たな欠落としては判定しなかった。

実 v62 には依頼成果物が1ファイル/1版の例しかなく、複数ファイル切替・複数版選択・成果物なしは実確認していない。存在しないケースを生成していない。今回は保存操作と画面の境界の検証であり、出典/日本語要約の意味的一致、モデルが述べた正確さ、過去の失敗を合格へ変更しない。人間受入、実iPhone、スクリーンリーダー、全ブラウザー適合、賞の水準達成を意味しない。

Home資料追加については、別担当の Home.tsx / paper.css 差分と実画像5枚を独立目視した。追加ボタン・添付済件数・一覧の状態が区別でき、以前のOSネイティブ未選択表示との矛盾はなくなった。320/390/1440/200%画像とfocus枠で新P1/P2を見つけていない。独立した操作再実行ではなく、OS chooserを開いて取消する挙動は担当者側も未確認として残している。

## 公開候補と私有データ

公開候補JSONと目視したWorkroom画像について、実鍵4値×16ファイルのバイト一致0、JSONのJWT/GitHub token/秘密鍵パターン一致0。検出の完全性を保証する検査ではない。`observe.mjs`、`adopt-rep4.mjs`、生 actions、ZIP、DB、設定、鍵、私有ログは公開対象外。画像ハッシュは `image-manifest.json`、安全な結果は `verification.json`。
