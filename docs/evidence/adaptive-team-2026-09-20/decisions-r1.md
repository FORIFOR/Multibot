# 注文フロー設計決定事項 (decisions.md)

## 1. 注文更新ロジック

### 1.1 イベント処理

注文更新イベントは以下の通り処理する：

- **new**: 注文作成完了
- **partial_fill**: 部分約定発生
- **fill**: 完全約定
- **canceled**: 取消完了
- **rejected**: 拒否
- **pending_cancel**: 取消待ち（取消完了ではない）

### 1.2 状態照合ロジック

再接続時の状態照合は以下の手順で行う：

1. サーバー側の注文状態を取得（client_order_id またはサービス側 ID で照会）
2. ローカル状態と照合
3. 差分を処理（再送、状態更新）
4. 照合失敗時はサーバー状態を優先し、再発注しない

### 1.3 再送重複防止

- idempotency key を使用
- 任意の HTTP 再送が安全でないことを考慮
- サーバー側の結果を信頼
- 発注要求をサーバー側で永続化

## 2. 部分約定・取消競合処理

### 2.1 部分約定処理

- 部分約定イベント（partial_fill）を受信
- 約定数量を更新
- 残り数量を計算（サーバー状態をベース）
- pending_cancel 中に部分約定が発生した場合、サーバー状態を優先

### 2.2 取消競合処理

- 取消リクエストと部分約定イベントの競合
- サーバー側の状態を優先
- ローカル状態とサーバー状態の差分を処理
- 取消待ち（pending_cancel）中の部分約定・累積約定量・残量はサーバー状態から取得

### 2.3 応答喪失時の処理

- 応答が来ない場合、ローカル状態を「未確定」として維持
- 再接続時にサーバー側から状態を取得し、差分を処理
- 照合失敗時に再発注しない（サーバー状態を優先）

## 3. 取消待ち状態の詳細処理

### 3.1 pending_cancel 状態遷移

取消リクエスト送信後の状態遷移と維持条件：

| 条件 | 状態遷移 | 累積約定量 | 残数量 | 処理 |
|------|----------|------------|--------|------|
| canceled イベント受信 | canceled → | 0 | 0 | 取消完了 |
| partial_fill イベント受信 | pending_cancel → partial_fill | 更新 | 更新 | サーバー状態を優先 |
| fill イベント受信 | pending_cancel → fill | 全約定 | 0 | 完全約定 |
| 取消要求拒否（サーバー側） | pending_cancel → new | 0 | 元の数量 | 再発注可能 |
| 応答喪失 | pending_cancel (unconfirmed) | 未確定 | 未確定 | 再接続時に照合 |
| 照合失敗 | pending_cancel (server_state) | サーバー状態 | サーバー状態 | 再発注しない |

### 3.2 累積約定量と残量の計算

- 累積約定量：partial_fill 及び fill イベントの約定数量の総和
- 残数量：元の数量 - 累積約定量
- サーバー状態をベースに更新

## 4. Paper/Live 切り替え条件

### 4.1 切り替え条件

- 設定ファイル経由での切り替え
- API キーと接続先の切り替え
- Paper/Live のフラグ管理
- 発注前に live/paper 環境を確認

### 4.2 制限事項

- Paper は実市場と同じ約定品質の証拠ではない
- 配当を模擬しない
- 注文数量を実際の NBBO 数量と照合しない
- Paper 成功を本番の収益性や流動性の保証にしない

### 4.3 Live 通過条件

- Paper 環境でのロジック検証完了
- 認証・秘鍵管理の検証完了
- 注文フローのイベント処理検証完了
- 再接続・状態照合の検証完了
- 本番接続（Live）への移行条件：
  - 上記検証が全て完了
  - 対象市場・証券会社の契約完了
  - 税務・法令上の適合性確認
  - ユーザーの Live 環境利用同意

## 5. 価格データ処理

### 5.1 取得時刻表示

- 価格の取得時刻を表示
- 古い価格をリアルタイムと称さない
- 元価格時刻と受信時刻による古さ判定を実装

### 5.2 利用権限表示

- 価格データの取得時刻と利用権限を表示
- 取得可否を UI に表示

## 6. 古さ判定ロジック

### 6.1 古さ判定条件

- 元価格時刻と受信時刻の差
- 評価時の現在時刻を含めた古さ判定
- 表示と実行可否の扱いを整合させる

### 6.2 表示と実行可否

- 取得時刻と古さフラグを表示
- 古い価格は実行対象外とする
- 古さ閾値による実行可否の判定

## 9. 境界定義の明確化

### 9.1 Core と証券 Adapter の境界

- Core：注文状態管理、イベント処理、重複防止、取消競合処理
- 証券 Adapter：証券会社 API 接続、注文・市場データ API、接続先スイッチング
- 永続化：発注要求をサーバー側で永続化（Core の責務）
- 秘鍵管理：Auth Layer の責務（証券 Adapter は永続化しない）

### 9.2 UI と Core の境界

- UI：表示・入力処理、認証セッション管理
- Core：状態管理、イベント処理
- UI はサーバー状態を信頼し、Core からの状態更新通知を受信

### 9.3 Auth Layer と External API Layer の境界

- Auth Layer：秘密鍵管理、認可チェック、Paper/Live 切り替え設定
- External API Layer：API 接続、接続先スイッチング
- 秘鍵は Auth Layer が管理し、External API Layer は永続化しない
