### 1.2 モジュール構成と責務

- **UI Layer**: 表示・入力処理（サーバー状態を信頼）
- **Auth Layer**: 認証・秘鍵管理・認可チェック（サーバー側永続化）
- **Order Flow Layer**: 注文フロー・状態管理（重複防止・取消競合・再接続照合）
- **Market Data Layer**: 市場データ取得・処理（古さ判定・利用権限表示）
- **External API Layer**: 外部 API 接続（接続先スイッチング）

### 1.3 各層の責務分担

## 2. モジュール詳細

### 2.1 UI Layer

- 表示内容：注文履歴、価格表示（取得時刻付き、古さフラグ付き）
- 入力処理：注文作成・更新・取消のフォーム
- 認証セッション管理：サーバーから状態取得
- 利用権限表示：価格データ取得可否を表示

### 2.2 Auth Layer

- 秘密鍵（API キー）はサーバーサイド格納
- ブラウザへの秘密鍵渡り禁止
- Paper/Live 切り替え：設定ファイル経由（環境変数または設定ファイル）
- 認可チェック：発注前にサーバー側で認可を確認
- 永続化：発注要求をサーバー側で永続化し、再送時にも同じ結果が返ることを保証

### 2.3 Order Flow Layer

- 注文作成・更新・取消の処理
- 部分約定・完全約定・取消のイベント処理
- **pending_cancel**: 取消待ち状態の維持
  - 取消リクエストを送信し、サーバーから取消完了イベント（canceled）を受信するまで、pending_cancel 状態を維持
  - 部分約定イベント（partial_fill）が pending_cancel 中に到着した場合、サーバー側の状態を優先
  - 累積約定量・残量の計算はサーバー状態をベースに更新
- 取消競合処理：
  - 取消リクエストと部分約定イベントの競合発生時、サーバー側の状態を優先
  - ローカル状態とサーバー状態の差分を処理
- 再送重複防止：
  - idempotency key を使用
  - 任意の HTTP 再送が安全でないことを考慮
  - サーバー側の結果を信頼
- 応答喪失時の処理：
  - 応答が来ない場合、ローカル状態を「未確定」として維持
  - 再接続時にサーバー側から状態を取得し、差分を処理
  - 照合失敗時に再発注しない（サーバー状態を優先）

### 2.4 Market Data Layer

- WebSocket 接続：
  - 注文更新ストリーム（trade_updates）購読
  - 価格データストリーム（別途購読必要）
- 価格データ取得：取得時刻付き
- 古さ判定：
  - 元価格時刻と受信時刻を比較
  - 古い価格をリアルタイムと称さない
  - 古さフラグを表示
- Paper/Live 環境切り替え

### 2.5 External API Layer

- 証券会社 API 接続（Alpaca 等の抽象化）
- 注文・市場データ API
- 接続先スイッチング（Paper↔Live）
- 接続失敗時の再試行ロジック

## 3. 状態管理

### 3.1 注文状態

- `new`: 注文作成済み
- `partial_fill`: 部分約定
- `fill`: 完全約定
- `canceled`: 取消済み
- `rejected`: 拒否
- `pending_cancel`: 取消待ち（取消完了ではない）

### 3.2 取消待ち状態の詳細（pending_cancel）

取消リクエスト送信後の状態遷移と維持条件：

| 条件 | 状態遷移 | 累積約定量 | 残数量 | 処理 |
|------|----------|------------|--------|------|
| canceled イベント受信 | canceled → | 0 | 0 | 取消完了 |
| partial_fill イベント受信 | pending_cancel → partial_fill | 更新 | 更新 | サーバー状態を優先 |
| fill イベント受信 | pending_cancel → fill | 全約定 | 0 | 完全約定 |
| 取消要求拒否（サーバー側） | pending_cancel → new | 0 | 元の数量 | 再発注可能 |
| 応答喪失 | pending_cancel (unconfirmed) | 未確定 | 未確定 | 再接続時に照合 |
| 照合失敗 | pending_cancel (server_state) | サーバー状態 | サーバー状態 | 再発注しない |

### 3.3 再接続時の状態照合

- 切断から再接続したら、口座・注文・約定を照合
- サーバー側の状態を信頼
- ローカル状態とサーバー状態の差分を処理
- 照合失敗時に再発注しない（サーバー状態を優先）

### 3.4 発注前の確認

発注前に以下の確認を行う：

- 口座情報
- 銘柄情報
- 売買可否
- 数量
- 価格条件
- 推定費用
- live/paper 環境

## 4. Core・証券 Adapter・UI の境界

### 4.1 Core（注文フロー層）

- 責務：注文状態管理、イベント処理、重複防止、取消競合処理
- 入力：UI からの注文要求（Auth Layer を経由）
- 出力：証券 Adapter への発注要求、UI への状態更新通知
- 永続化：発注要求をサーバー側で永続化（idempotency key など）
- 照会：応答喪失時のサーバー側状態照会

### 4.2 証券 Adapter（外部接続層）

- 責務：証券会社 API 接続、注文・市場データ API、接続先スイッチング
- 入力：Core からの発注要求、市場データ購読要求
- 出力：証券会社からの応答（注文状態、価格データ）
- 抽象化：市場・証券会社・認証方式の未決定事項を抽象層で隠蔽
- 永続化：API キーの管理（Auth Layer との境界）

### 4.3 UI（表示層）

- 責務：表示・入力処理、認証セッション管理
- 入力：ユーザー操作、Core からの状態更新通知
- 出力：注文要求（Core 経由）
- 制限：秘密鍵を渡さない、サーバー状態を信頼

- 利用地域

- 税務・法令上の適合性
- Live 通過条件（本番接続までの段階と通過条件の詳細）

## 6. 提案する実装段階と通過条件

### 6.1 Paper 環境でのロジック検証

- 注文フローのイベント処理検証（new/partial_fill/fill/canceled/rejected）
- 取消競合処理検証
- 再接続・状態照合検証
- 重複防止検証（idempotency key）
- 古さ判定ロジック検証

### 6.2 Live 通過条件

- Paper 環境でのロジック検証完了
- 認証・秘鍵管理の検証完了
- 注文フローのイベント処理検証完了
- 再接続・状態照合の検証完了
- 対象市場・証券会社の契約完了
- 税務・法令上の適合性確認
- ユーザーの Live 環境利用同意
- 本番接続（Live）への移行

## 7. 価格データ処理

### 7.1 取得時刻表示

- 価格の取得時刻を表示
- 古い価格をリアルタイムと称さない
- 元価格時刻と受信時刻による古さ判定を実装

### 7.2 利用権限表示

- 価格データの取得時刻と利用権限を表示
- 取得可否を UI に表示
