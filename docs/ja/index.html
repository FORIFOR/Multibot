仕組み

Master が計画し、Bot が作り、Runtime が確かめる。

1. 計画は構造化出力

Master が成果物・完了条件・タスクの依存関係を出す。Runtime がスキーマ、循環、担当、ツール範囲、書込範囲を検証し、通らない計画は 1 度だけ差し戻す。

2. 作業は実メッセージと実ファイル

Bot 間の送信は相手の受信箱に届く事実の記録で、台本ではない。成果物は SHA-256 付きの改訂として不変に保存される。

3. 検証は改訂に束ねる

検査とレビュー判定は改訂ハッシュに結び付く。最終報告はイベント記録から組み立てるので、モデルの要約が「着手」を「完了」に格上げできない。

予算・回数上限・権限・承認・停止はプロンプトではなく Runtime が強制。Builder / Reviewer のコマンドは Docker（ネットワーク遮断・読み取り専用）か macOS の seatbelt で実行し、どちらも無ければ実行を拒否します。

失敗と部分完了の理由

1 回目の失敗は、レビュー待ちのタスクに依存する別タスクが永遠に待つスケジューラの不具合でした（修正し、テストを追加）。再実行は指摘の修正と再検証まで進みましたが、レビュー・セッションが予算上限 $1.5 に 2 度達し、原文の逐一照合を残して partial になりました。調査系の依頼は最も費用が高く、最も安定しません。
