# Requester-owned delivery requirements

An API caller can attach up to ten `inputs.delivery_requirements`, each containing a normalized relative `logical_path` and a nonempty JSON Schema (at most 64 KB). They are persisted with the original request and passed to the planner/workers. The master cannot erase these requirements by creating weaker task acceptance criteria. See the source-derived construction in `backend/scripts/production_workflow.py` for a real use case.

When a task publishes a required output, `finish_task` checks the latest bytes, stored SHA-256 and schema. Failure returns concrete problems so the worker can publish another revision. Automatic task completion uses the same check. Final run completion checks every required path, including missing outputs; failure produces `partial`, never `completed`. A `delivery.checked` event binds each result to its artifact revision/hash and requirement hash. Results appear in the final report and event timeline. Review decisions remain separately visible.

JSON Schema and regex checks use a separate Python process with a two-second CPU limit, five-second wall limit and, on Linux, 512 MiB address-space limit. Input is capped at 2 MB and reported output at 64 KB. Remote references, schema IDs and dynamic/recursive references are rejected; local JSON Pointer references are supported. Unsupported/invalid/excessive checks return `blocked` and cannot authorize completion. Other programmatic checks retain their existing behavior. This is a bounded pure-data validator, not a general code-execution sandbox.

`read_input_file` retrieves only text already supplied with the request, by exact unambiguous attachment name. It exposes source SHA-256, character range and whether more text remains, and records `input.read`. It cannot read arbitrary host paths or invent artifact revisions. The same source remains available inline in worker context.

Requirements are opt-in for API callers; the current browser composer does not configure them. Existing requests without requirements retain their prior acceptance flow. The schema author must encode the actual business conditions. A Japanese-character pattern or valid JSON does not prove faithful translation, factual accuracy, safety of downstream actions or overall task success. Model review and meaningful workflow evaluation remain necessary. Source files and schema are part of the model input and must follow the deployment's data policy.
