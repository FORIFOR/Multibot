# Contract First Build

## Goal
一つの価値あるフローを実際に動かし、別の開発者がCoreを改変せず利用・拡張できる最小の契約を作る。レイヤーを分けることと、大規模な分散システムを作ることは別である。

## Read first
[共通の証拠・権限契約](references/evidence-contract.md)を読む。既存の指示と作業差分を保護する。言語・framework・ビルド・テスト・契約の既存実装を確認し、書き込みが許可された対象だけを変更する。

## Workflow
1. 既存の正常系と失敗例を再現し、受け入れ条件と非対象を先に固定する。元から失敗するテストや環境依存の失敗を記録する。
2. Input / Output / Error / State / Event / Permissionを必要な範囲だけ定義する。JSON Schema等の既存基盤を使い、公開する部分と内部詳細を分ける。
3. 成熟した規格に合う部分はAdapterで接続する。公称互換と部分対応を区別し、対象バージョンと未対応項目を明記する。既存構造で成立するなら新しいパッケージ分割は不要。
4. Coreはルールと状態、Adapterは外部接続、UIは表示と入力を担う。同じ業務ルールをGUIとCLIに二重実装しない。ネイティブ製品にWeb用のライブラリを導入するためだけの移植をしない。
5. 外部副作用のある処理は、実行前の承認、費用の提示、冪等性、重複防止、状態照会、失敗／未確認時の復帰をリスクに応じて設計する。LLMの判断だけを権限境界にしない。サーバー／信頼できる実行層で検証する。
6. UIと実装の状態を一致させる。受付を完了と表示しない。取り消せない外部処理で偽の取消ボタンを出さず、停止できる範囲を説明する。
7. 入力から成果物までの縦一貫フローを最初に作る。大量の画面、複数プロバイダー、管理画面を先に増やさない。デモがfixtureでも同じ契約とUI経路を利用し、実サービス試験は別に用意する。
8. 単体・契約・統合・実画面E2Eのうち必要な試験を実装する。永続CI検証が必要ならPlaywright Test等を明示して使い、探索用ブラウザーSkillの結果だけで済ませない。
9. 起動手順、サンプル、SDK例、変更履歴、互換性と移行方法、権限説明を変更と同時に更新する。存在しないコマンドやAPIをREADMEに書かない。
10. 独立検証用に対象revision、差分、起動手順、試験データ、受け入れ条件、証拠の場所を引き渡す。実装者の自評を合格の根拠にしない。

## Stability
公開契約のstable/experimentalを明記する。過去バージョンの代表fixtureや外部クライアントを使う互換テストを追加する。破壊的変更が避けられない場合は、廃止手順、移行例、影響を示し、承認された範囲でのみ行う。

## Done means
そのrevisionで、主フローの実行証拠、関連テストの最新出力、説明と実装の対応が揃うこと。安全上重大な欠陥、主要価値の不成立、承認外の副作用が残る場合はリリース可能と報告しない。

## UI handoff
UI変更時はworld-class-uiのデザイン方針と状態を受け取り、token・component・業務状態を接続する。
本Skillが業務ルール、world-class-uiがUIの造形と相互作用を担当し、同一ファイルの競合編集を避ける。
実装後にworld-class-uiで実画面を仕上げ、その後に独立検証へ渡す。UI変更がないタスクで装飾を追加しない。
