# Outcome First UX

## Goal
説明を読まなくても「何ができる・次に何をする・何が起きた・どう戻す」が分かる主フローを作る。説明を不要にすることと、ラベル・フィードバックを消すことを混同しない。

## Read first
[共通の証拠・権限契約](references/evidence-contract.md)を読む。既存製品の目的、ブランド制約、技術基盤、状態モデル、アクセシビリティ要件、既存UIを確認する。実装許可がなければ設計案と検証計画のみを出す。

## Workflow
1. 最も重要なユーザーの仕事を一つ選び、「最初に見えるもの→最小の入力→結果→次の操作」を書く。設定画面や空のチャット画面を出発点に決めつけない。
2. 新規利用者が最初に知る必要のないプロバイダー、Webhook、トークン上限、エージェント内部状態は詳細設定へ移す。ただし費用、送信先、権限、取り消し不能性など実行判断に必要な情報は隠さない。
3. 空、入力中、接続待ち、処理中、承認待ち、成功、失敗、キャンセル、外部結果未確認の状態を、実装が持つ状態と対応付ける。結果未確認を成功や単純失敗に誤変換しない。
4. 既存ブランドに従い、情報構造と主要フローの案を比較して絞る。world-class-ui併用時はここで主タスク・情報順・状態を引き渡し、視覚の方向性決定・UI実装・仕上げを同Skillへ集約する。全製品の構図やデモを一律にしない。
5. world-class-uiが導入済みならUIの視覚と操作の仕上げに使用する。単独利用なら同じ原則で仕上げる。追加の見た目の補助はfrontend-designまたはImpeccable等の選定済み一系統だけを使う。外部Skillの一般的な好みは、ユーザーの明示したブランド、プラットフォーム慣習、アクセシビリティより優先しない。
6. 手動入力に加えて編集可能なサンプルを用意する。デモデータは明示し、実際の成果物と同じ閲覧・編集UIを通す。サンプルが成功しただけで実サービスの動作を保証しない。
7. ボタンは結果が分かる動詞で命名する。表示上の名称と通知・完了表示の語を統一する。アイコンだけの主操作、hover限定の必須操作、キーボードショートカットだけの導線を避ける。
8. Webなら狭幅、標準スマホ、タブレット、デスクトップ、200%拡大、日本語IME、長文、キーボード、フォーカス、読み上げ、reduced motionを検証する。ネイティブは実際のプラットフォームのUI試験を別に行う。
9. 実画面を起動し、主フローの録画と状態別スクリーンショットを確認して修正する。DOMやスクリーンショットだけでは業務成果の検証にならないため結果の証拠も取る。
10. 人間の初見ユーザー評価を計画する。AI初見テストはヒューリスティックな補助であり、人間の成功率とは区別する。

## Required artifacts
既存の相当ドキュメントを優先し、なければPRODUCT.mdに製品事実、DESIGN.mdに製品固有の表現、受け入れ条件に主フローと状態を記録する。修正前後の差、残る障害、未実施項目も示す。

## Do not
装飾、最新ライブラリ、グラデーション、グラス表現、常時モーション、カード数の増加を品質の代わりにしない。全機能をチャットに閉じ込めない。フォーム項目を単に隠して安全説明を失わせない。FigmaやWeb上の成功からネイティブ実装まで検証したと主張しない。
