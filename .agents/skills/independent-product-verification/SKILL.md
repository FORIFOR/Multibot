# Independent Product Verification

## Goal
見栄えや実装者の説明に引きずられず、ユーザーの目的が本当に成立するか確認する。可能なら実装者と別セッションで行う。同じモデルの別セッションも完全な独立評価ではなく、人間の評価を置き換えない。

## Read first
[共通の証拠・権限契約](references/evidence-contract.md)を読む。対象revisionと受け入れ条件、実行の許可範囲を確認する。最初のUX試験ではユーザーのタスクと安全な起動情報だけを受け取り、ボタン位置や正解ルートを先に読まない。

## Pass A: First-use behavior
1. 許可されたクリーンなテスト環境で起動する。導入の時間は依存物のDL、モデルのDL、アカウント準備を含むか明記する。できなければ理由をBLOCKEDで記録する。
2. 主フローを自力で見つけ、開始、進捗確認、成果物の確認、修正／保存まで行う。助言を読んだら補助ありとして記録する。AIによる探索を「初見ユーザー5人」と偽装しない。
3. 失敗、権限拒否、接続切断、二重クリック、取消、再接続、結果未確認、長文、空データを対象に合わせて試す。危険な本番操作は承認済みsandbox/テストアカウントでのみ実行する。
4. モバイル幅、キーボード、フォーカス、読み上げ、日本語IME、200%拡大、reduced motionを対象に合わせて検証する。自動a11yチェックだけで完全準拠と断定しない。
5. クリック後の見た目だけでなく、成果物・保存状態・外部処理結果を照合する。費用や送信を伴うものは副作用も確認する。

## Pass B: Technical checks
6. ここで実装・仕様・差分を読む。境界、認証認可、機密情報、公開契約の互換性、導入/アンインストール手順を確認する。
7. 関連するbuild、typecheck、test、E2Eを実際に実行し、完全な出力とexit codeを読む。存在しないコマンドを仮定しない。テストを変更・削除して合格にしない。
8. Web Vitalsのフィールド計測とラボ計測は別に記録する。Lighthouseの単発結果を実利用者のp75と呼ばない。ネイティブの動作はネイティブの環境で確認する。
9. 同一タスク・端末・データ・バージョンで比較可能な場合にのみ競合比較を行う。比較できない機能の優劣や企業全体への優位性を断定しない。

## Output
各チェックを id / method / expected / observed / status / evidence / environment で出す。P0欠陥と主要価値不成立を最優先し、見た目の点数と平均して打ち消さない。合計点を出すより証拠付きの未達を示す。

変更は原則行わず、実装担当へ再現手順付きの修正依頼を返す。テストデータ生成と証拠保存は許可範囲内で行い、場所を報告する。独立検証のために許可なく別repo、別worktree、クラウド費用を発生させない。

## Pass C: Visual and interaction craft
初見操作の後、実画像を開いて主役・情報順・日本語改行・余白・整列・密度・素材・製品固有の表現を確認する。
主画面だけでなく結果・失敗・狭幅も確認する。保存しただけの画像を目視レビュー済みとしない。
操作・録画で反応と遷移を確認し、静止画からanimationの品質を断定しない。
見た目と操作成功を別々に判定する。具体的な欠陥は修正要求、主観的な好みはsuggestionとして分ける。
合意したデザイン方針の未実装を見逃さず、合計点で主タスク失敗や危険を相殺しない。
比較対象のホームページの魅力と、対象アプリのタスク効率を混同しない。
