# OSS Standard Audit

## Goal
「人気のあるアプリ」と「他者が独立に実装・利用できる共通契約」を分けて評価し、対象製品の一つの主要タスクについて、最小限で実行可能な改善案を作る。

## Read first
[共通の証拠・権限契約](references/evidence-contract.md)を読む。既存のAGENTS.md、CLAUDE.md、製品説明、実際の起動手順、関連するソース・テストを確認する。既存ドキュメントが同じ役割を担うなら新しい正本を増やさない。

## Workflow
1. 対象ユーザー、ユーザーの一つの仕事、成果物、既存の代替手段を特定する。不明事項はリポジトリと依頼文から調査し、不可逆でない部分は仮定を明示して進める。
2. READMEの主要な主張を、実装箇所と実行可能なデモに対応付ける。存在、静的確認、実行確認を区別する。
3. 参考を最大3種類に絞る。普及しているアプリ、相互運用の仕様、同じタスクの競合。公式資料と関連する実ソースを読み、URL、参照日時、ref/commitまたは取得できたblob SHAを記録する。星数は確認日時付きの注目指標であって標準化の証明ではない。
4. 標準化する境界を一つ選ぶ。対象は入出力、イベント、データ形式、拡張契約など。既存規格をそのまま使う、薄いAdapterで接続する、独自拡張が必要、の三つに分類する。OpenAPI、MCP、AG-UI等を名前のためだけに全部導入しない。
5. 拡張のためにCore改変が必要か、UIなしで中核が使えるか、ベンダーを交換できるか、旧バージョンとの互換性をテストできるかを調べる。必要のない別プロセス・別repo・マイクロサービス化を避ける。
6. 冷たい初回環境からの導入、サンプル体験、本番接続、失敗時の復帰、削除／エクスポートを確認する。デモがモックなら明記し、本番動作済みと扱わない。
7. 公開API、ライセンス条件、SECURITY/CONTRIBUTING、変更方針、互換テスト、SDK例、独立実装・外部採用の有無を分けて判定する。自社製品同士の連携は独立採用とは別に記録する。
8. P0=誤動作/危険/主要価値不成立、P1=初回成功や互換性を妨げる、P2=磨き込み、で優先順位を付ける。各提案に対象ファイル、期待する効果、受け入れ条件、依存・リスク、変更しないものを添える。

## Output
- 結論: 製品としての普及と契約としての普及を別々に判定。
- 証拠表: claim / source file or official spec / validation level / gap。
- 最小の標準化境界、既存規格との対応、作らない独自仕様。
- 一つの主要フロー、比較対象、測定条件、受け入れ条件の案。
- 優先修正3件と保留理由。調査許可だけならここで止め、コードや公開設定を変更しない。

## Do not
「Open」を名乗るだけで標準化と評価しない。星数の多さから使いやすさの原因を断定しない。他社や他製品より優れているという主張は同条件の検証なしに書かない。対象repoを読まずに一般論だけで採点しない。
